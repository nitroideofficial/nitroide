The PWA Recipe: Manifest, Service Worker, and Install Prompt for a Static Site.

A PWA is not a framework. It is three small pieces that agree with each other: a manifest that describes your app, a service worker that controls its network, and an install prompt that appears at the right moment. No app store, no build step, no backend — which is exactly why it fits a static site. I run NitroIDE, a browser IDE, as a PWA on GitHub Pages, and the whole recipe is three files and one event listener. Here it is, with the traps I actually hit.

Piece 1: the manifest — fifteen lines that make you an app

The manifest is a JSON file that tells the browser what your site is when it stops being a tab. Mine is short enough to quote in full:

{
  "name": "NitroIDE",
  "short_name": "NitroIDE",
  "description": "Zero-latency, client-side browser IDE for HTML, CSS, and JS.",
  "start_url": "/index.html",
  "display": "standalone",
  "background_color": "#0a0a0a",
  "theme_color": "#0a0a0a",
  "orientation": "any",
  "icons": [
    { "src": "/favicon-192x192.png", "sizes": "192x192", "type": "image/png", "purpose": "any" },
    { "src": "/favicon-192x192.png", "sizes": "192x192", "type": "image/png", "purpose": "maskable" },
    { "src": "/icon-512x512.png", "sizes": "512x512", "type": "image/png", "purpose": "any" }
  ]
}

Linked from the page with <link rel="manifest" href="manifest.json">. The fields that actually matter: display: "standalone" removes the browser chrome so the installed app feels like an app, not a bookmark; start_url is where the app opens; theme_color paints the status bar; and the icons need both a 192 and a 512, with one marked maskable so Android can crop it into its adaptive icon shape without cutting off your logo. Skip the maskable entry and your icon arrives pre-cropped by the OS, which is how nice logos end up with their corners eaten.

Piece 2: the service worker — two caches, two strategies

The service worker is the piece people overbuild. Mine does four things: precache the app shell, serve pages network-first, serve heavy vendor files cache-first, and never cache anything it shouldn't.

The shape that matters is the two-cache split. The app-shell cache (nitroide-v375, bumped on every deploy) holds the pages, CSS, JS, fonts and icons. The vendor cache (nitroide-vendor-v1, bumped only when a file under /vendor/ actually changes) holds the big stable stuff. The reason is deploy frequency: the site's publishing pipeline bumps the app cache several times a day, and every wipe used to force a full re-download of Monaco — about 10MB — on the next editor visit. Separating the caches means deploys stay cheap and the editor stays fast.

The fetch handler is two strategies, chosen per request:

  • Network-first for documents and the main bundles (pages, script.js, styles.css). A deploy shows up on the next refresh instead of hiding behind the cache. The cache is the offline fallback, not the source of truth.
  • Cache-first for vendor assets (fonts, icons, Monaco). These change rarely and cost the most to fetch, so a cache hit is the fast path.

And three rules that guard the whole thing:

  1. Only same-origin GET requests. The worker never touches anything else — no cross-origin fetches, no POSTs.
  2. Never cache a failed response. A cached 404 or 500 keeps serving the failure after the network recovers. The handler checks response.ok before every cache.put.
  3. Never cache what must stay live. /api/* (the forms backend), ads.txt, llms.txt, the RSS feeds and the dev.to snapshot are all bypassed. Share links (?code=...) are cached under the bare path, so a thousand unique share URLs can't bloat the cache with a thousand copies of the same shell.

Two more decisions worth stealing. First, Monaco is not precached anymore. A homepage visitor who never opens the IDE used to download ~10MB of editor during service-worker install; now it is runtime-cached on first IDE use. Precaching is for the shell, not for the heaviest thing you own. Second, a failed precache fails the install — loudly. If one file in the app shell 404s, the worker throws, the old worker keeps serving, and the browser retries on the next navigation. A half-populated cache is worse than no update at all.

Piece 3: the install prompt — catch the event, don't chase it

The browser fires beforeinstallprompt when your site is installable, and it fires it once. If you don't catch it, the browser shows its own mini-infobar and you get no second chance in that session. The recipe is to catch it, stash it, and show your own button:

window.addEventListener('beforeinstallprompt', (e) => {
  e.preventDefault();
  deferredPrompt = e;
  showInstallButton();
});

NitroIDE's install lives in the IDE itself — an "Install App" item in the Prefs menu — because that is where a user decides the tool is worth keeping. The button appears when the event fires and disappears on appinstalled. The part people forget is the platforms that never fire the event at all: iOS has no beforeinstallprompt, so the same menu item shows a hint instead — "To install on iOS: tap Share, then 'Add to Home Screen'." And on desktop browsers without the event, the fallback points at the browser menu. One menu item, three paths, no dead ends.

The update dance — the part that traps users on old code

A new service worker does not take over immediately. It installs, waits, and only activates when every tab using the old one closes — which, for a tool people leave open, can be never. The fix is a small handshake: the worker calls skipWaiting() after a successful precache, and the page listens for controllerchange and shows a toast — "New version available" with a Refresh button. Registration itself is two lines with one guard that matters: only on HTTPS, and updateViaCache: "none" so the browser always checks for a new worker instead of serving a cached copy of the worker itself. Skip that option and your update check can be cached for a day, which is exactly how users end up running last week's code and reporting bugs you already fixed.

The checklist

If you are adding this to a static site, the whole recipe fits on an index card:

  1. Manifest with standalone, a start_url, theme color, and 192 + 512 icons including one maskable.
  2. Service worker, HTTPS only, updateViaCache: "none".
  3. Two caches: one for the app shell (bumped per deploy), one for stable vendor files.
  4. Network-first for pages and main bundles; cache-first for heavy vendor assets.
  5. Never cache failures, never cache /api/* or anything that must stay live, and never precache your heaviest dependency.
  6. Catch beforeinstallprompt, show your own install button, and write the iOS hint by hand — it will never fire there.
  7. skipWaiting after a successful precache, and a "New version available" toast on controllerchange.

That is the whole thing. No store review, no binary, no backend — a static site that installs like an app, works offline, and updates itself with a toast instead of a trap.

Frequently asked questions

Why does NitroIDE use two service worker caches?

The app-shell cache is bumped on every deploy, which happens several times a day — and every wipe used to force a full re-download of Monaco, about 10MB, on the next editor visit. The vendor cache only changes when a file under /vendor/ actually changes, so deploys stay cheap and the editor stays fast.

Why isn't Monaco precached?

A homepage visitor who never opens the IDE used to download ~10MB of editor during service-worker install. Now Monaco is runtime-cached on first IDE use instead. Precaching is for the app shell, not for the heaviest thing you own.

How do I install NitroIDE on iOS?

iOS has no beforeinstallprompt event, so there is no install button to catch. In the IDE, open the Prefs menu and choose "Install App" — on iOS it shows the hint instead: tap Share, then "Add to Home Screen".
