Measuring the Feedback Loop: Keystroke to Pixels, Timed End to End.

Every browser IDE claims its preview is "instant". I got tired of saying it about NitroIDE without a number, so I timed it — real keystrokes into the real editor, end to end, five trials per path. Here are the numbers, medians first:

  • CSS edit, keystroke to applied: 150ms
  • HTML edit, keystroke to painted: 550ms
  • Manual Run click to painted: 61ms

The interesting part isn't the totals. It's where the time goes.

How I measured it

A harness typed real characters into the real Monaco editors in a local copy of the codebox, and timed each path to the preview's own signal: the preview-painted message the preview posts back on a double requestAnimationFrame after the new frame loads. Five trials per path, medians reported, headless Chromium 157 on a 4-core VM, default workspace, no CDN links.

Small doc, so treat the rebuild numbers as best-case. The debounce numbers are constants from the code — those hold everywhere.

The numbers, decomposed

A CSS edit takes 150ms, and the debounce is 150ms. That means the work itself costs about zero: one update-css postMessage rewrites the live <style> tag inside the running preview. No reload, no new iframe, no lost JS state. The proof is in what didn't happen: across ten CSS trials, the preview reported zero repaints.

An HTML edit takes 550ms, and the debounce is 500ms. The rest — a full rebuild from srcdoc, new iframe, fresh JS context, re-run your script, wait for paint — is only 50 to 70ms. The Run button proves it: click to painted, with no debounce in the way, is 61ms.

So the loop is debounce-bound, not render-bound. The preview itself is fast. The wait you feel is a pause the code inserts on purpose.

Why 500ms and not 50

Because a rebuild on every keystroke would thrash. Each rebuild is a new iframe and a fresh JS context. Typing "hello" would be five rebuilds, five script re-runs, five paints — most of them thrown away before you ever saw them. The debounce trades half a second of latency for zero wasted work. CSS gets the shorter 150ms pause because applying a style edit in place is nearly free, so there is almost nothing to protect against.

One honest footnote: the first keystroke after load is slower — 700 to 960ms in my runs. That's cold iframe warm-up, not a steady-state cost. It only happens once per session.

The flicker fix, verified in passing

The rebuild swaps the new frame in only after it has actually painted — the double-requestAnimationFrame signal, with a 1,500ms fallback. That fallback never fired in any trial. It exists for the slow case; on a small doc the paint signal always wins first.

What this doesn't prove

A heavy page costs more. Big JS, CDN scripts, a large DOM — all of that lands in the 50–70ms rebuild step, which grows with your document. The debounce doesn't grow: 150 and 500ms are constants, whatever you type. So if your loop feels slow, look at your document weight first, not the editor.

And "instant" deserves its honest version: 550ms for HTML, 150ms for CSS on a small doc — and about 90% of the HTML number is a deliberate pause. If I ever lower the debounce, I'll say so with new numbers, not adjectives.
